# 인공지능 구조 원리 교과서 — 자료 페이지

> ## ⚠ 동기화 규칙 — 가장 먼저 읽을 것
>
> `notebooks/` 아래의 `.ipynb` 는 **구글 드라이브 원본의 사본**이다.
>
> **드라이브 원본을 고치면 이 사본도 반드시 함께 고친다.**
>
> 이 규칙이 깨지면 점검 도구가 독자가 실제로 여는 것과 다른 코드를
> 검사하게 된다. 통과해도 아무 의미가 없어지고, 오히려 "점검하고
> 있다"는 잘못된 안심만 남는다.
>
> 사본에 검증 셀을 추가하지 말 것. 검증은 `checks/verify_results.py`
> 가 실행 결과를 바깥에서 읽어 판정한다.
>
> **파일명은 Colab 원본 이름을 그대로 쓴다.** Colab 의 "GitHub 에 사본
> 저장"이 그 이름으로 덮어쓰기 때문이다. 여기서 이름을 바꾸면 다음
> 저장 때 원래 이름으로 파일이 하나 더 생기고, 이름을 바꿔 둔 쪽이
> 낡은 사본으로 남는다.

공개 주소: <https://mlfundamentals.github.io/ai-structure/>

## 구성

```
index.html                 사이트 (data/*.json 을 읽어 상태를 표시)
links.yml                  점검 대상 URL 51건 — 사이트 섹션 2의 원본
notebooks.yml              실행·검증 대상과 판정 규칙
notebooks/                 드라이브 원본의 사본 6개 (Colab 이름 그대로)
checks/check_links.py      A. 링크 점검
checks/verify_results.py   C. 실행·결과 검증
checks/manual_checklist.md 분기 실환경 점검 목록 (이슈 본문이 된다)
data/links.json            링크 점검 결과 (워크플로가 커밋)
data/status.json           STATUS 섹션 데이터 · 마지막 실환경 점검일
requirements-notebooks.txt 노트북 실행 의존성
.github/workflows/         links.yml(주 1회) · notebooks.yml(월 1회)
                           manual-check.yml(분기 · 이슈만 연다)
.nojekyll                  GitHub Pages 가 파일을 그대로 서빙하게 함
```

사이트 섹션 2에 보이는 내용을 바꿀 때는 `index.html` 이 아니라
`links.yml` 을 고친다. 점검 결과는 워크플로가 `data/` 에 써 넣고
페이지가 읽는다.

**섹션 1(본문 실습 카드)만 예외다.** 손으로 쓴 HTML 이고, 데이터에서
받는 것은 `data-nb` 로 붙는 상태 배지뿐이다.

### ⚠ 이름이 같은 파일이 둘 있다

`notebooks.yml` 은 루트의 **설정 파일**, `.github/workflows/notebooks.yml`
은 **워크플로**다. 한 번 서로 덮어써서 실행 점검이 통째로 사라진 적이
있다. 워크플로 쪽 첫 줄은 항상 `name: 실습 실행 점검` 이어야 한다.

## 실습은 6개 + 그림 1개다

본문 실습 **6개**(60·73·85·103·108·220쪽)와 188쪽 GIF 그림 **1개**.
합쳐서 링크 7건이다.

188쪽을 실습으로 세는 바람에 여섯 자리가 채워져, **103쪽 CNN 실습이
사이트에서 통째로 빠져 있던 적이 있다**(2026-09-09 발견). 개수를 셀
때는 "실습 6 + 그림 1"로 나눠 센다.

## 점검 체계

| | 주기 | 하는 일 |
|---|---|---|
| **A 링크** | 주 1회 (월요일) | `links.yml` 의 URL 51건에 요청 |
| **B 실행** | 월 1회 (1일) | 노트북 사본 6개를 `nbconvert --execute` 로 실행 |
| **C 결과** | B와 함께 | 실행 결과의 핵심 수치가 기대 범위 안인지 판정 |
| **실환경** | 분기 (1·4·7·10월) · 수동 | 사람이 실제로 열어 확인. **알림만 자동** |

분기 알림은 `.github/workflows/manual-check.yml` 이 이슈를 연다.
마지막 점검일은 **`data/status.json` 의 `manual.checked` 하나**에서
읽는다 — 사이트 STATUS 표에 찍히는 바로 그 날짜다. 출처가 하나뿐이라
어긋남이 없다. 점검을 하고도 그 값을 안 고치면 이슈가 계속 열린다.
**그게 맞다.**

예약 실행은 저장소가 60일 조용하면 멈춘다. 90일 주기라 혼자서는
스스로를 못 깨운다. **주간 링크 점검의 커밋이 깨워 두고 있다.**

### 403을 실패로 처리하지 않는다

위키백과·위키독스·아마존·네이버는 자동화 요청을 차단한다. 403을 실패로
처리하면 매주 거짓 경보가 오고, 결국 알림을 통째로 무시하게 된다.
`403`·`429`·타임아웃은 **확인 필요**로만 기록하고, 워크플로를
실패시키는 것은 `404`·`410` 뿐이다.

차단이 확실한 사이트는 `links.yml` 에 `expect_block: true` 를 달아
아예 판정 대상에서 뺀다. **본문 실습 링크 7건이 전부 여기 해당한다** —
네이버 단축 URL이고, GitHub Actions 러너는 미국 데이터센터 IP다.
이 7건은 자동 점검으로는 확인되지 않으므로, 분기별 실환경 점검에서
사람이 직접 연다.

### ⚠ 살아 있는 잘못된 링크는 자동으로 못 잡는다

URL 오기는 두 종류다. 같은 실수인데 한쪽만 자동으로 잡힌다.

| | 무슨 일이 벌어지나 | 누가 잡나 |
|---|---|---|
| **103쪽** | 오타가 우연히 **살아 있는 다른 주소**가 됐다. 85쪽 실습이 열린다 | 사람이 열어봐야 안다 |
| **66쪽** | 오타가 **존재하지 않는 경로**가 됐다(`tensorflow-` ← `kr` 누락) | 링크 체커가 404 로 즉시 |

**"열린다"와 "올바른 것이 열린다"는 다른 확인이다.**
분기 수동 점검이 존재하는 이유가 여기 있다.

### `resolved` 는 기록이지 점검 대상이 아니다

`links.yml` 의 `resolved` 에는 네이버 단축 URL 7건의 최종 주소가 적혀
있다(2026-09-10 기록). 단축 서비스가 종료되면 이 기록이 실습 자료에
닿는 유일한 경로다 — 본문에는 단축 주소만 인쇄돼 있다.

**그러나 이 값을 자동 점검에 넣지 말 것.** Colab 의 `/drive/<ID>` 주소는
노트북이 삭제되거나 공유가 끊겨도 로그인 화면 HTML 과 함께 200 을
반환한다(2026-09-10 실측). 점검 대상에 넣으면 영원히 초록 불이 켜지고,
그것은 66쪽 때보다 나쁘다 — 그때는 몰랐지만 이번엔 "점검하고 있다"고
착각하게 된다.

`checks/check_links.py` 는 `expect_block` 항목을 아예 요청하지 않고
`resolved` 값을 그대로 기록만 한다. 지금 구조가 맞다.

### 사이트의 '실습 열기' 는 드라이브 원본으로 간다

배지는 `notebooks/` 사본의 실행 결과이고, '실습 열기' 는 드라이브
원본으로 간다. **둘이 다른 파일이라는 것을 알고 그렇게 두었다** —
사본을 원본과 같게 유지하는 것이 위 동기화 규칙의 전제다.
후속편(`making-ai`)도 같은 원칙으로 되어 있다.

링크를 네이버 단축이 아니라 최종 주소로 건 이유는, 이 페이지가
**단축 주소 쪽에 문제가 생겼을 때 오는 곳**이기 때문이다. 그 통로가
다시 같은 단축 서비스를 거치면 의미가 없다.

### 화면에 무엇을 보여줄지 — `audience`

기준은 하나다. **이 주소가 죽으면 독자가 무언가를 못 하게 되는가.**

- **된다 → `audience: reader`.** 강의·문서·영상·도구는 독자가 열려고
  인쇄된 것이다. 죽으면 갈 곳을 잃는다. **늘 보이는 11건**
- **안 된다 → `audience: record`.** 그림 출처는 그림이 이미 책에 실려
  있다. 저작권과 예의의 표기지 독자가 열어볼 것이 아니다. **접히는 33건**

**점검은 51건 전부 그대로 한다.** 화면에 보이는 것만 줄인 것이다.
`links.yml` 에서 지우면 66쪽 같은 것을 다시는 못 잡는다.
접힌 항목도 죽거나 확인이 필요해지면 위 목록으로 올라온다.

### ⚠ CI는 Colab보다 엄격하다 — 그게 목적이다

Colab은 기존 노트북이 깨지지 않도록 `TF_USE_LEGACY_KERAS=1` 같은 호환
설정을 켜 두는 경우가 있다. 그 상태에서는 Keras 2에서만 동작하는 옛 API
(예: `optimizer.minimize()`)가 그대로 돈다.

**CI에는 그 설정을 켜지 말 것.** CI가 먼저 실패해 주는 것이 이 점검의
목적이다. Colab이 호환 스위치를 내리는 날 독자 환경이 한꺼번에 깨지는데,
그 전에 알려 주는 유일한 장치가 이 워크플로다.

"CI에서만 실패한다"는 것은 정상이 아니라 **경보**다. 워크플로에
`TF_USE_LEGACY_KERAS` 를 추가해 통과시키지 말고, 노트북 코드를
새 API로 고쳐 양쪽에서 돌게 만든다. (예: `optimizer.minimize(cost, var_list)`
→ `tf.GradientTape` + `optimizer.apply_gradients()`. 후자는 Keras 2에도
있으므로 옛 환경에서도 그대로 동작한다.)

라이브러리 버전은 고정하지 않는다. **노후화 감지가 이 점검의 목적이다.**
GPU 빌드는 깔지 않는다 — `tensorflow-cpu`, torch 는 CPU 전용 인덱스에서
이름으로 지목해 받는다.

### 판정 원칙 — 기본은 "오류 없이 끝까지 실행됐는가" 하나

수치 검사는 실행 점검이 **원리적으로** 잡지 못하는 곳에만 둔다.
지금은 두 곳뿐이다.

- **85쪽** — 오류 없이 잘 돌아가면서 본문 논지를 뒤집을 수 있다
- **60쪽** — 오류 없이 수렴만 실패할 수 있다

수치 규칙을 늘리기 전에 **"이건 실행 점검으로 안 잡히는가"를 먼저
물을 것.** 규칙이 늘수록 노트북이 아니라 규칙이 고장 나서 거짓 경보가
난다. 2026-09-08 에 규칙 세 개가 전부 잘못 걸려 있었고, 노트북은
멀쩡했다.

108·220쪽은 마지막에 `input()` 대화형 루프가 있어 CI 에서
`StdinNotImplementedError` 로 끝난다. 이 오류 하나만 예외로 넘긴다.

### ⚠ 85쪽만 판정 방향이 반대다

85쪽 퍼셉트론 XOR은 **실패를 보여주는 실습**이다. 천 번을 학습시켜도
오차가 줄지 않는 것이 정상이고, 그것이 다층 퍼셉트론으로 넘어가는
근거다.

라이브러리 기본값이 바뀌어 **우연히 학습에 성공해 버리면 본문 논지가
정반대로 뒤집힌다.** 그래서 이 예제만 "성공하면 경보"다.

`notebooks.yml` 의 `practice-085` 에 `assert: {gt: 1.5}` 로 적혀
있다. 출력에 `accuracy` 가 없고 `Epoch: 100 | Cost: 4` 형식이므로
**마지막 Cost 가 크게 남아 있어야 정상**이다. 이 파일에서 유일하게
"성공하면 경보"인 항목이다. **뒤집지 말 것.**

### ⚠ 인쇄 쪽수와 PDF 쪽수는 4쪽 차이다

`인쇄 쪽 + 4 = PDF 쪽`. 참고 문헌과 그림 출처의 원문은 **인쇄
226~227쪽**(PDF 230~231쪽)이다. 지난 기록이 이 둘을 섞어 적어
"230~231쪽"이라는 잘못된 안내가 여러 세션 굳어 있었다. 책의
230~231쪽은 찾아보기다. 쪽수를 적을 때는 **어느 쪽인지 밝힐 것.**

`links.yml` 의 그림 출처 `page` 는 **그림이 실린 본문 쪽**이다.
출처 목록이 실린 쪽은 `listed_on` 에 따로 적는다. 같은 주소가 여러
쪽에 쓰였어도 항목을 합치지 않는다 — 독자가 "171쪽"으로 찾을 수
있어야 한다.

## 운영 원칙

1. **책을 고치지 말고 페이지를 고친다.** 링크가 죽거나 코드가 낡으면
   사이트에서 대응하고, 본문 수정은 다음 쇄로 미룬다.
2. **자료실 코드가 항상 최신이다.** 책과 다를 수 있음을 명시하고,
   고친 부분에 주석을 단다.
3. **정오표는 쇄별로 구분한다.**
4. **빈 섹션도 남긴다.** "아직 보고된 오류가 없습니다"가 섹션을
   감추는 것보다 신뢰를 준다.
5. **점검 결과를 숨기지 않는다.** 관리되고 있다는 사실 자체가 신호다.
6. **커스텀 도메인을 쓰지 않는다.** 도메인 만료가 링크 소실보다 위험하다.
7. **UPDATES 게시일은 수기로 적는다.** 빌드 시각으로 자동화하면 오타
   수정에도 날짜가 바뀌어 "새 소식"으로 잘못 읽힌다.
